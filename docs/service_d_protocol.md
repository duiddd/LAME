# Service D: Risk Control — Communication Protocol

**Owner:** Zongyan Yang · **Status:** draft, updated on 2026-11-06 after the team discussion and after reading A's and B's latest code (A's `feature/trading`, B's `resume_ok`).

This document defines the interfaces between D and A and B. The design background is in [service_d_architecture.md](service_d_architecture.md), and the reasons are in [service_d_tech_decisions.md](service_d_tech_decisions.md). For D ↔ B, B's implementation is the reference (`match_engine/doc/runtime.md` on the `feature/match_engine` branch).

## 0. Communication methods and common conventions

**Communication methods (RD23):** only two transports, and all data is JSON.

| Situation | Method | Interfaces in this document |
| --- | --- | --- |
| Request-response | HTTP + JSON | A → D place, cancel, modify, query; D → A notifications |
| Continuous push | WebSocket + JSON, with a resume handshake | D ↔ B |
| Monitoring | HTTP `/metrics` | Prometheus scrapes D |

**Common conventions:**

- **Prices and quantities are integers**: a price is a whole number of ticks and a quantity a whole number of lots (B document D5). A and the frontend convert to and from decimals.
- All times are Unix milliseconds as integers.
- Field names use `snake_case`; enums are uppercase strings.
- **Two kinds of order ID (RD24):**
  - `order_id`: a ULID string generated by A (A document D4). It is used only between A and D, and both A and D key on it.
  - `b_order_id`: an integer assigned by D and used only between D and B (B's `order_id` is a `u64`). D assigns it from a **global counter that is never reset**, so it never repeats for a user within a day (B document D2). After a modify, one `order_id` maps to several `b_order_id`s.
  - `order_seq`: the number B gives an order when it accepts it. B's `trade` refers to orders by it.
- `user_id`: A's integer user ID. D passes it to B unchanged.
- `symbol`: written like `BTC-USDT`. Names follow B's pair list; A uses the same names. It must be a pair in the symbol config (section 5).
- `day`: B's trading day, the Dublin local date, as `YYYY-MM-DD`. A record from B is identified by `(day, seq)`, and `seq` restarts from 1 every day.
- Ports: D's HTTP interface is on **8400**, A's on **8000**, B's control port on **11659**. All of them are open only inside the compose network.

## 1. Overview

```
        ① POST /v1/orders, /v1/cancels, /v1/modifies
        ④ GET  /v1/orders/{order_id}                         ② WS /d (B's protocol)
  A ─────────────────────────────────────────► D ═══════════════════════════► B
    ◄───────────────────────────────────────── │  new_order / cancel_order     │
        synchronous reply: "received" only     │ ◄═══════════════════════════  │
                                              │  order_event / trade (all)    │
  A ◄──────────────────────────────────────── D
        ③ POST /internal/order-events (D pushes every outcome)

  Shared config files (read by A, B and D): linked accounts, trading pairs (section 5)
```

| No. | Direction | Method | Purpose | Owner |
| --- | --- | --- | --- | --- |
| ① | A → D | HTTP | Place, cancel, modify | D defines, A reviews |
| ② | D ↔ B | WebSocket | D sends commands; all of B's outputs go to D | B defines, D follows |
| ③ | D → A | HTTP | Notify A of the risk decision and of B's results | Delivery rules defined by A (A document 3.1, D21); notification fields defined by D, A reviews |
| ④ | A → D | HTTP | Query an order's state by `order_id`, for reconciliation | D defines, A reviews |

**Basic rule:** D's synchronous reply to A **only means that D has received the request**. The risk decision, B's results, trades and cancel results all reach A as notifications on ③ (RD11, RD6).

## 2. A → D: HTTP interface

### 2.1 Place order `POST /v1/orders`

**Request**

```json
{
  "order_id": "01JBCX3K8Q6W2ZP4V7N9R5T1YM",
  "user_id": 1024,
  "symbol": "BTC-USDT",
  "side": "BUY",
  "type": "LIMIT",
  "price": 6425000,
  "qty": 3
}
```

| Field | Notes |
| --- | --- |
| `side` | `BUY` / `SELL` |
| `type` | `LIMIT` / `MARKET` (renamed to `order_type` when D sends it to B) |
| `price` | Required for limit orders; must be `null` or absent for market orders |
| `qty` | Positive integer (number of lots) |

**Synchronous processing** (all before the reply, and fast):

1. Check the format, the symbol and the tick/lot grid. If any check fails, reply 400.
2. Idempotency: if `(user_id, order_id)` already exists, reply 202 with the current state when the content is the same, and 409 when it is different (2.5).
3. If D is not ready, reply 503 `RISK_UNAVAILABLE`; if the decision queue is full, reply 503 `RISK_BUSY`. **On a 503, D keeps no record of the order**, so when A later resends the same `order_id`, D treats it as a new order (RD11).
4. Store the order (state `RECEIVED`), put it into the decision queue, and reply 202.

**Asynchronous processing** (after the reply):

5. If a cancel for this `order_id` arrived earlier (a tombstone), reject with `CANCELLED_BEFORE_SUBMIT`.
6. Decide by the rules (R1, R2) within `GATE_DEADLINE`; if the deadline passes, reject with `RISK_TIMEOUT`.
7. Write the decision to the database. If approved, assign the `b_order_id` in the same transaction.
8. Rejected: notify A with `RISK_REJECTED`. Approved: send `new_order` to B; from then on every output of B is turned into a notification for A (section 3).

**Synchronous reply**

| Status | Body | Meaning | What A does |
| --- | --- | --- | --- |
| 202 | `{"order_id": "...", "status": "RECEIVED"}` (for a repeated request, `status` is the current state) | D has received it | Order becomes `SENT`; the hold is kept until a notification arrives |
| 400 | `{"error": "INVALID_REQUEST", "message": "..."}` | The order never entered D | The hold can be released |
| 409 | `{"error": "ORDER_ID_CONFLICT"}` | The same `order_id` exists with different content | A bug in A; do not release the hold |
| 503 | `{"error": "RISK_UNAVAILABLE"}` or `{"error": "RISK_BUSY"}` | D did not take the order and keeps no record | Under A's current rules this is "no acknowledgement": resend the same `order_id`, and send a cancel after `RESEND_WINDOW` (the cancel gets `TOMBSTONED`). A needs no change. Later A may treat 503 as "certainly not received" and release the hold at once |
| Connection failure / timeout | — | A does not know whether D received it | Same as above |

### 2.2 Cancel `POST /v1/cancels`

**Request**

```json
{ "user_id": 1024, "order_id": "01JBCX3K8Q..." }
```

Cancels are not checked against the rules. D handles a cancel according to the order's state inside D (architecture document section 6):

| State inside D | What D does | `action` in the reply | Notifications that follow |
| --- | --- | --- | --- |
| Not known | Records a tombstone; a later order with this ID is rejected | `TOMBSTONED` | `CANCEL_RESULT TOMBSTONED` |
| `RECEIVED` (no decision yet) | Takes it out of the decision queue and records it as rejected | `NOT_SENT_TO_B` | `RISK_REJECTED CANCELLED_BEFORE_SUBMIT`, then `CANCEL_RESULT NOT_SENT_TO_B` |
| `REJECTED_BY_D` | Nothing | `NOT_SENT_TO_B` | `CANCEL_RESULT NOT_SENT_TO_B` |
| `LIVE` | Sends `cancel_order` to B at once | `SENT` | `ORDER_UPDATE CANCELLED`, then `CANCEL_RESULT CANCELLED` |
| `IN_FLIGHT` / `TIMED_OUT` | Sends only after `sent_at + MAX_COMMAND_AGE + CANCEL_MARGIN` (RD13) | `SCHEDULED` | According to B's result |
| Final (filled, cancelled, rejected) | Does not send to B | `ALREADY_FINAL` | `CANCEL_RESULT ALREADY_FINAL` |
| Disconnected from B | Queues it and sends after reconnecting and catching up | `QUEUED` | According to B's result |

**Reply (HTTP 202)**

```json
{ "user_id": 1024, "order_id": "01JBCX3K8Q...", "action": "SCHEDULED", "send_not_before": 1793270400725 }
```

- Cancels are idempotent: repeating a cancel does not send it to B twice.
- The reply only tells A what D plans to do. **The result of the cancel is the `CANCEL_RESULT` notification.**

### 2.3 Modify `POST /v1/modifies`

The proposal says that a modify is sent to D under the same `order_id`, and becomes "cancel + new order" at B (proposal lines 55 and 84). So D does the translation (RD27).

**Request**

```json
{ "user_id": 1024, "order_id": "01JBCX3K8Q...", "price": 6420000, "qty": 2 }
```

`qty` is the new **remaining** quantity (A document 5.4); `price` can be left out if it does not change.

Only limit orders that B has accepted (`LIVE` in D) can be modified.

**What D does** (rules agreed with A, A document 5.4):

1. Record the modify and send `cancel_order` for the order's current `b_order_id`. D remembers how much had filled at that moment.
2. When B answers `CANCELLED`: the new quantity is `qty` minus what filled while the cancel was on its way, so the user never gets more than they asked for. Then check the new price and quantity against the rules as a new order (R1, R2), on the book without the old order.
3. If they pass: assign a new `b_order_id` and send `new_order`. From then on, the events of every `b_order_id` of this order are translated back to the same `order_id`, and the filled quantity adds them together.
4. When B accepts the new order, notify `MODIFY_RESULT APPLIED` with the actual `price` and `qty`. D sends no `ORDER_UPDATE CANCELLED` and no second `ACCEPTED` for a successful modify.

When the modify cannot go ahead:

| Case | Notifications |
| --- | --- |
| The order is already final, or B has not accepted it yet | `MODIFY_RESULT REJECTED` (`ALREADY_FINAL` / `NOT_MODIFIABLE`); the order stays as it is |
| A cancel from A is already pending | `MODIFY_RESULT REJECTED` `CANCEL_PENDING` |
| The old order fills completely during the cancel | `ORDER_UPDATE FILLED`, then `MODIFY_RESULT REJECTED` `ALREADY_FINAL` |
| Nothing is left after subtracting the fills | `ORDER_UPDATE CANCELLED`, then `MODIFY_RESULT REJECTED` `ALREADY_FINAL` |
| The new order fails the rules | `ORDER_UPDATE CANCELLED` (reason `SELF_TRADE` / `WASH_TRADE`), then `MODIFY_RESULT REJECTED` with the same reason |
| B rejects the new order, or it never reaches B | `ORDER_UPDATE` (`REJECTED` / `EXPIRED`, or `REJECTED NOT_DELIVERED`), then `MODIFY_RESULT REJECTED` with the same reason |
| A cancels while the old order is being cancelled | `MODIFY_RESULT REJECTED` `CANCELLED_BY_USER`, then the usual `ORDER_UPDATE CANCELLED` and `CANCEL_RESULT` |

A cancel that arrives after the new order was sent applies to the new order as usual.

**Reply:** 202 `{"user_id": 1024, "order_id": "...", "action": "CANCELLING"}` (or `"action": "DONE"` with `result` and `reason` when it was refused at once). The same modify sent again gets the same reply; a different modify while one is pending gets 409 `MODIFY_IN_PROGRESS`; an unknown order gets 404; a market order or a bad price/qty gets 400; while D is not ready, 503 `RISK_UNAVAILABLE` with no record kept.

The order is off the book between the cancel and the new order and loses its time priority. This is accepted, since B has no amend (A document 5.4).

### 2.4 Query `GET /v1/orders/{order_id}?user_id=1024`

Used by A for reconciliation (A document section 9). Read-only; it changes nothing.

```json
{
  "order_id": "01JBCX3K8Q...", "user_id": 1024,
  "state": "LIVE",
  "decision": "APPROVED", "reason": null,
  "filled_qty": 1, "remaining_qty": 2,
  "last_notify_seq": 5821
}
```

| Field | Notes |
| --- | --- |
| `state` | State inside D (architecture document section 6): `RECEIVED`, `REJECTED_BY_D`, `IN_FLIGHT`, `TIMED_OUT`, `LIVE`, `MODIFYING`, `FILLED`, `CANCELLED`, `REJECTED_BY_B`, `NOT_DELIVERED` |
| `last_notify_seq` | The number of the last notification about this order. If A's cursor is smaller, a notification has not reached A yet |

- If D does not know the `order_id`: 404. A can resend the same `order_id`, or cancel.
- The query result itself never releases funds; only notifications do (A document D5).

### 2.5 Idempotency rules

- Idempotency key: `(user_id, order_id)`.
- A repeated order request with the same content: reply 202 with the current state; D does not decide again and does not send to B again.
- A repeated order request with different content: 409 `ORDER_ID_CONFLICT`. A modify must go through `/v1/modifies`.
- Guarantee: **an approved order is sent to B at most once; an order D rejected is never sent to B.**

### 2.6 Other endpoints

| Path | Purpose |
| --- | --- |
| `POST /v1/notifications/rewind` | `{"from_seq": N}`: when A finds a missing notification, it asks D to resend from N (A document section 9) |
| `GET /healthz` | 200 when ready, otherwise 503 with a body saying which condition is not met |
| `GET /metrics` | Prometheus format |
| `POST /admin/faults` | Fault-injection switches; exists only when `FAULTS_ENABLED=true` |

## 3. D → A: notifications `POST /internal/order-events`

### 3.1 Delivery rules (following A document 3.1 and D21)

- Address: `http://service-a:8000/internal/order-events`.
- Every notification carries a `notify_seq` assigned by D. It starts from 1 and is **contiguous across the whole system, and is not reset across trading days**.
- D sends **one notification at a time, in order**. Until A answers 2xx, D resends the same one (with a growing interval).
- A's answers:
  - `200`: committed, or a duplicate. D sends the next one.
  - `409 {"expected_seq": N}`: there is a gap. D resends from N.
  - Anything else, or a connection failure: D resends the same one later.
- Notifications waiting to be sent are stored in D's database (the outbox), so after a restart D continues and nothing is lost (RD25).
- While A is down, notifications queue in D's outbox; D's decisions and its link to B are not affected.

### 3.2 Common fields

```json
{
  "notify_seq": 5821,
  "type": "TRADE",
  "order_id": "01JBCX3K8Q...",
  "user_id": 1024,
  "symbol": "BTC-USDT",
  "b_day": "2026-11-05",
  "b_seq": 18343,
  "ts": 1793270400130
}
```

| Field | Notes |
| --- | --- |
| `notify_seq` | Notification number; A uses it to deduplicate and to find gaps |
| `type` | One of the six types (3.3) |
| `order_id`, `user_id` | A's order ID and user ID. For `TRADE` these two fields are in `taker` and `maker` instead (3.3) |
| `b_day`, `b_seq` | For notifications that come from B, the `(day, seq)` of B's record; `null` otherwise |
| `ts` | When D generated the notification |

### 3.3 The six notification types

The type names follow A document 3.1. Below are only the fields specific to each type.

**`RISK_REJECTED`**: D rejected the order; it was not sent to B.

```json
{ "reason": "WASH_TRADE", "rule_version": "v1-3fa9c2" }
```

`reason`: `SELF_TRADE`, `WASH_TRADE`, `RISK_TIMEOUT`, `CANCELLED_BEFORE_SUBMIT`.

**`ACCEPTED`**: B accepted the order (B's first `order_event`; B guarantees that `ACCEPTED` always comes first).

```json
{ "order_seq": 18342, "rule_version": "v1-3fa9c2" }
```

A uses `(b_day, order_seq)` as the order's number at B (A's `b_order_seq`).

**`TRADE`**: one trade. Both sides are in the same notification, so A can settle both in one transaction (A document 5.3).

```json
{
  "price": 6424000, "qty": 1,
  "taker": { "order_id": "01JBCX3K8Q...", "user_id": 1024, "side": "BUY" },
  "maker": { "order_id": "01JBCW9P2M...", "user_id": 2077, "side": "SELL" }
}
```

- The common `order_id` and `user_id` are empty; both sides are in `taker` and `maker`.
- B's `trade` only carries `taker_seq` and `maker_seq`; D translates them to `order_id`s with its ID map (RD24).
- A deduplicates trades by `(b_day, b_seq)` (the primary key of A's `trades` table).

**`ORDER_UPDATE`**: the order's state changed.

```json
{ "status": "CANCELLED", "reason": "END_OF_DAY", "filled_qty": 1, "remaining_qty": 0 }
```

| `status` | Source |
| --- | --- |
| `PARTIALLY_FILLED` / `FILLED` | B's `order_event` |
| `CANCELLED` | B's cancel result. `reason` can be `null` (user cancel), `END_OF_DAY`, `SELF_TRADE_PREVENTED`, or `D_TIMEOUT` when D cancelled it automatically after a timeout |
| `REJECTED` | B rejected the order, with `reason` `INVALID_PRICE`, `INVALID_QTY` or `END_OF_DAY`; or the order never reached B, with `reason` `NOT_DELIVERED` (section 4.5) |
| `EXPIRED` | When B answers `REJECTED` + `EXPIRED`, D turns it into `status = EXPIRED`, as A's document writes it |

- `filled_qty` is the **cumulative filled quantity**. After a modify, one `order_id` has several `b_order_id`s, and the cumulative quantity adds them together.
- `remaining_qty` is the quantity still resting on the book.

**`CANCEL_RESULT`**: the result of a cancel sent by A.

```json
{ "result": "CANCELLED" }
```

| `result` | Meaning |
| --- | --- |
| `CANCELLED` | Cancelled (an `ORDER_UPDATE CANCELLED` was sent before this) |
| `TOMBSTONED` | D never received this order; it recorded a tombstone and will not accept the order later |
| `NOT_SENT_TO_B` | D did not approve this order (a `RISK_REJECTED` was sent already) |
| `ORDER_NOT_FOUND` | The order never reached B and never will (RD13) |
| `ALREADY_FINAL` | The order is already filled or otherwise final; it cannot be cancelled |

**`MODIFY_RESULT`**: the result of a modify (section 2.3).

```json
{ "result": "APPLIED", "price": 6420000, "qty": 2, "reason": null, "order_seq": 57 }
```

- `result`: `APPLIED` or `REJECTED`.
- For `APPLIED`, `price` and `qty` are what is now on the book (`qty` is the remaining quantity, possibly less than A asked for), and `order_seq` is the new order's position at B.
- For `REJECTED`, `reason` is one of `ALREADY_FINAL`, `NOT_MODIFIABLE`, `CANCEL_PENDING`, `CANCELLED_BY_USER`, `SELF_TRADE`, `WASH_TRADE`, `NOT_DELIVERED`, or B's reason (`EXPIRED`, `INVALID_PRICE`, ...).

### 3.4 Order

- Notifications are sent in the order D processes them. For notifications that come from B, this is B's `seq` order.
- For one order, `ACCEPTED` always comes before its `TRADE`s. One match at B outputs `trade`, the taker's `order_event`, then the maker's `order_event`, and D turns them into `TRADE`, `ORDER_UPDATE`, `ORDER_UPDATE` in that order.
- `ORDER_UPDATE CANCELLED` always comes before the matching `CANCEL_RESULT CANCELLED`.

### 3.5 When A releases funds

A defines the release rules (A document 5.2). This table only checks which notifications D sends:

| D's notification | What A does with the hold |
| --- | --- |
| `RISK_REJECTED` | Release the whole hold |
| `ORDER_UPDATE` `REJECTED` / `EXPIRED` | Release the whole hold |
| `ORDER_UPDATE` `CANCELLED` | Release the unfilled part only |
| `ORDER_UPDATE` `FILLED` | Nothing yet; wait for the trades to settle |
| `CANCEL_RESULT` `TOMBSTONED` / `ORDER_NOT_FOUND` | Release what remains |
| `TRADE` | Settle that quantity |

A 202 reply, a query result and a timeout never release funds.

## 4. D ↔ B

B's implementation is the reference (`match_engine/doc/runtime.md`).

### 4.1 Connection

- Address: `ws://service-b:11659/d`. Only one connection at a time; a new connection closes the old one.
- The first message must be `{"type":"resume","from_seq":N}`. B answers first with `{"type":"resume_ok","from_seq":N,"through_seq":M}`, where `M` is the last output stored at that moment, then resends its current day's outputs with `seq > N`, and at the same time pushes new outputs.
- D asks from its last applied `seq` when that was today, and from 0 otherwise (for example after a night away). B moves to a new day only when the first command of the new day arrives, and all commands come from D, so after a night away B may still be serving the old day. Asking from 0 covers both cases; records D already applied are dropped by `(day, seq)`.
  - Reconnect: N = the largest `seq` D has applied.
  - D restart: N = 0, and D rebuilds its features from the start of the day (RD15).
  - New trading day: start from 0.
- B pings every 5 seconds and closes a connection that has been silent for 15 seconds. B also closes the connection when its queue to D is full. In both cases D reconnects and resumes.
- D's network must be in B's `CTRL_ALLOWED_CIDRS`.

### 4.2 From D to B

```json
{"type":"new_order","symbol":"BTC-USDT","order_id":481,"user_id":1024,"side":"BUY",
 "order_type":"LIMIT","price":6425000,"qty":3,"origin":"USER","sent_at":1793270400125}
{"type":"cancel_order","symbol":"BTC-USDT","user_id":1024,"order_id":481}
```

- `order_id` is the `b_order_id` assigned by D, not A's ULID.
- `sent_at` is D's clock, read just before sending.
- A cancel names its target by `(user_id, b_order_id)`.
- `origin` is always `USER`; no `LIQUIDATION` orders in the core (RD20).
- `new_order` is sent only after the decision (and the `b_order_id`) is committed (RD8).

### 4.3 From B to D

```json
{"type":"order_event","day":"2026-11-05","seq":4,"prev_seq":2,"symbol":"BTC-USDT",
 "order_seq":3,"order_id":481,"user_id":1024,"status":"ACCEPTED","filled":0,"remaining":3,"reason":null}
{"type":"trade","day":"2026-11-05","seq":5,"prev_seq":4,"symbol":"BTC-USDT",
 "price":6424000,"qty":1,"taker_seq":3,"maker_seq":1,"taker_user_id":1024,"maker_user_id":2077}
```

- `status`: `ACCEPTED`, `PARTIALLY_FILLED`, `FILLED`, `CANCELLED`, `REJECTED`.
- `reason`: `ORDER_NOT_FOUND`, `SELF_TRADE_PREVENTED`, `EXPIRED`, `END_OF_DAY`, `INVALID_PRICE`, `INVALID_QTY`.
- `prev_seq` is the `seq` of the previous **output**. Commands also take a `seq`, so the `seq`s of outputs are not contiguous, and `prev_seq` is what shows whether the chain is complete.
- A rejected cancel carries only the IDs the cancel itself named (`user_id`, `order_id`), and no `order_seq`.
- For a malformed command, B answers `{"type":"error","code":...}`. Such a reply has no `seq` and is not recorded. D validates before sending, so this should not happen; if it does, D logs an alert and the order is handled as a timeout (section 4.5).

### 4.4 How D handles B's outputs

- **Deduplication:** the resend and the live push can interleave and repeat, so D deduplicates by `(day, seq)`.
- **Applying in chain order:** if a record arrives before the one it follows, D buffers it and applies it once the `prev_seq` chain connects, so every output is applied exactly once and in B's order. If a gap is not filled within `GAP_TIMEOUT_MS`, D disconnects and reconnects.
- **Catching up (RD16):** D is caught up once its chain is contiguous up to `through_seq` from `resume_ok`, in the day being resent; records after it are live. If `through_seq ≤ from_seq` there is nothing to resend. For a B without `resume_ok`, D falls back to: the chain is contiguous and no new output has arrived for `CATCHUP_QUIET_MS`.
- **Translating IDs:** the `order_id` in an `order_event` is a `b_order_id`, and a `trade` uses `order_seq`. D translates both to A's `order_id` with its ID map (RD24).
- **Generating notifications:** each output updates the features and is turned into the matching notification in the outbox. After a restart, when D replays the day's outputs from 0, outputs that already produced notifications do not produce them again (RD15).

### 4.5 Timeouts and order fate (RD13)

- B's `MAX_COMMAND_AGE` is **1000 ms**, fixed at build time. D's `D_TIMEOUT` must not be smaller.
- If D sends a `new_order` and receives no output for that order within `D_TIMEOUT`, the order becomes `TIMED_OUT`. B's document requires D to cancel in this case, so D sends `cancel_order` **automatically** after `sent_at + MAX_COMMAND_AGE + CANCEL_MARGIN`.
- B's answer then:
  - `CANCELLED`: the order was on the book and is now cancelled. D notifies `ORDER_UPDATE CANCELLED` with reason `D_TIMEOUT`.
  - `REJECTED` + `ORDER_NOT_FOUND`: B has no such order. B does not tell "never arrived" from "already final", so D decides itself. If D has received outputs for this order, the order is final and those outputs stand. If not, the order **never reached B and never will** (the age limit has passed, so a late `new_order` would get `EXPIRED`), and D notifies `ORDER_UPDATE REJECTED` with reason `NOT_DELIVERED`.
- If an output for the order arrives before the cancel is sent (B was only slow), D drops the automatic cancel and the order becomes `LIVE` as usual.
- While D is disconnected from B, automatic cancels wait. After reconnecting and catching up, D checks again: if it has seen outputs for the order by then, it does not cancel.
- D and B run on the same host, so their clocks can be compared. B's D15 already relies on this.

### 4.6 Trading hours

D does not check trading hours. B rejects new orders outside 00:00–23:00 Dublin time and cancels all resting orders at 23:00, in both cases with reason `END_OF_DAY`. D handles these as ordinary rejections and cancels and turns them into notifications. On a new trading day `seq` restarts from 1, and D deduplicates by `(day, seq)`. Because B only moves to the new day when D sends its first command of that day, D gets the old day's last outputs (including the 23:00 cancels) even if it was down over midnight. The only case that loses them is B also restarting after midnight while D is down; we accept this.

## 5. Shared config files (read by A, B and D)

Two static files in one shared folder (for example `config/`), mounted into A, B and D in compose (RD17, RD28). D reads them once at start-up and does not refresh them.

## 6. What A does when D does not answer

A's full rules are in A document sections 5, 9 and 10. This section only covers the parts that involve D's interface:

| Situation | What A does | What D guarantees |
| --- | --- | --- |
| No 202 for an order (timeout, connection failure, 503) | Keep the hold, mark the order `UNKNOWN`; resend the same `order_id`; after `RESEND_WINDOW`, cancel | Resends are deduplicated by `order_id`; a cancel that arrives first leaves a tombstone and gets `CANCEL_RESULT TOMBSTONED` |
| 202 received, but no notification for a long time | Order stays `SENT`; query with backoff (2.4) | As long as D is running, every order reaches a final state (`GATE_DEADLINE`, the automatic cancel in 4.5) |
| A query shows a missing notification | Call `POST /v1/notifications/rewind` | The outbox keeps sent notifications, so they can be resent |
| D is completely down | Keep the holds; the circuit breaker opens, new orders get `SYSTEM_BUSY`, cancels are queued; wait for D | Decisions, the ID map, tombstones and the outbox are all in the database; after a restart D resumes from B and catches up, then answers queries and sends notifications |

## 7. Error codes

**D's rejection reasons (`reason` in `RISK_REJECTED`); all of them mean the order was not sent to B:**

| Reason | Meaning |
| --- | --- |
| `SELF_TRADE` | Could trade against the user's own resting order |
| `WASH_TRADE` | Could trade against a linked account's resting order |
| `RISK_TIMEOUT` | No decision within `GATE_DEADLINE` |
| `CANCELLED_BEFORE_SUBMIT` | A cancel for this ID arrived earlier |

**D's synchronous errors:** `INVALID_REQUEST` (400), `ORDER_ID_CONFLICT` (409), `RISK_UNAVAILABLE` (503, D not ready), `RISK_BUSY` (503, decision queue full).

**B's reasons:** `ORDER_NOT_FOUND`, `SELF_TRADE_PREVENTED`, `EXPIRED`, `END_OF_DAY`, `INVALID_PRICE`, `INVALID_QTY` (B's implementation).

**Reasons added by D:** `D_TIMEOUT` (D cancelled after a timeout), `NOT_DELIVERED` (the order never reached B).
