# Service D: Risk Control — Communication Protocol

**Owner:** Zongyan Yang · **Status:** draft, for team discussion

This document defines the interfaces between D and A and B, and what D requires from the "B → A event subscription". The design background is in [service_d_architecture.md](service_d_architecture.md), and the reasons are in [service_d_tech_decisions.md](service_d_tech_decisions.md).

Field names and formats follow the current draft. **The exact fields will be fixed after the team agrees on common conventions.**

## 0. Communication methods and common conventions

**Communication methods (RD23):** the team uses only two transports, and all data is JSON.

| Situation | Method | Interfaces in this document |
| --- | --- | --- |
| Request-response | HTTP + JSON | A → D place order, cancel; D → A load linked accounts |
| Continuous push | WebSocket + JSON, with a resume handshake where nothing may be lost | D ↔ B; B → A event subscription |
| Monitoring | HTTP `/metrics` | Prometheus scrapes D |

**Common conventions (draft):**

- **Prices and quantities are integers**: a price is a whole number of ticks and a quantity a whole number of lots (B document D5). A and the frontend convert to and from decimals.
- All times are Unix milliseconds as integers.
- Field names use `snake_case`; enums are uppercase strings.
- `order_id`: a ULID string generated by A (A document D4), so it never repeats for the same `user_id` within a trading day (B document D2).
- `user_id`: a string; D passes it to B unchanged.
- `symbol`: for example `BTC-USDT`; it must be a pair in B's configuration.
- A record from B is identified by `(day, seq)`.
- D's HTTP interface is on port **8400**, open only inside the compose network.

## 1. Overview

```
        ① POST /v1/orders, /v1/cancels           ② WS /d (B's protocol)
  A ─────────────────────────────────► D ═══════════════════════════► B
    ◄───────────────────────────────── │   NewOrder / CancelOrder     │
        D's decision + B's first result │ ◄═══════════════════════════ │
                                       │   OrderEvent / Trade (all)   │
        ④ GET /internal/linked-groups  │                              │
  A ◄───────────────────────────────── D                              │
                                                                      │
  A ◄═════════ ③ B's read-only event subscription (A connects to B directly, with resume) ═┘
```

| No. | Direction | Method | Purpose | Owner |
| --- | --- | --- | --- | --- |
| ① | A → D | HTTP | Place order, cancel | D defines, A reviews |
| ② | D ↔ B | WebSocket | D sends commands; all of B's outputs go to D | B defines (B document sections 2 and 6) |
| ③ | B → A | WebSocket | `OrderEvent` / `Trade` for A's settlement | B defines, A reviews; D only states requirements (section 4) |
| ④ | D → A | HTTP | Load linked accounts | A defines, D reviews |

## 2. A → D: HTTP interface

### 2.1 Place order `POST /v1/orders`

**Request**

```json
{
  "order_id": "01JBCX3K8Q6W2ZP4V7N9R5T1YM",
  "user_id": "u_1024",
  "symbol": "BTC-USDT",
  "side": "BUY",
  "type": "LIMIT",
  "price": 6425000,
  "qty": 3
}
```

| Field | Notes |
| --- | --- |
| `side` | `BUY` / `SELL` |
| `type` | `LIMIT` / `MARKET` |
| `price` | Required for limit orders; must be `null` or absent for market orders |
| `qty` | Positive integer (number of lots) |

**Processing**

1. Idempotency check: if `(user_id, order_id)` already exists, return the recorded result; do not decide or send again (2.3).
2. If a cancel for this order ID arrived earlier (D's local tombstone), reject with `CANCELLED_BEFORE_SUBMIT`.
3. If D is not ready, reject with `RISK_UNAVAILABLE`.
4. Put the order into the decision queue. If no decision is made within `GATE_DEADLINE`, reject with `RISK_TIMEOUT`.
5. Decide by the rules (R1, R2). The decision is written to the database first.
6. Rejected: return at once. Approved: send `NewOrder` to B and wait for B's first `OrderEvent` for this order, for at most `D_TIMEOUT`.

**Response (HTTP 200)**, four cases:

D rejects:

```json
{
  "order_id": "01JBCX3K8Q...", "user_id": "u_1024",
  "decision": "REJECTED",
  "reason": "WASH_TRADE",
  "rule_version": "v1-3fa9c2",
  "decided_at": 1793270400123
}
```

D approves, B accepts (`b_status` is the status of B's first `OrderEvent`: `ACCEPTED`, `PARTIALLY_FILLED` or `FILLED`):

```json
{
  "order_id": "01JBCX3K8Q...", "user_id": "u_1024",
  "decision": "APPROVED",
  "rule_version": "v1-3fa9c2",
  "b_result": "ACCEPTED",
  "b_status": "ACCEPTED",
  "day": "2026-10-29", "order_seq": 18342, "event_seq": 18343
}
```

D approves, B rejects (for example `EXPIRED`, or a price off the tick grid):

```json
{
  "decision": "APPROVED", "rule_version": "v1-3fa9c2",
  "b_result": "REJECTED", "b_reason": "EXPIRED",
  "day": "2026-10-29", "event_seq": 18343
}
```

D approves, no reply from B within `D_TIMEOUT`:

```json
{
  "decision": "APPROVED", "rule_version": "v1-3fa9c2",
  "b_result": "UNKNOWN",
  "sent_at": 1793270400125
}
```

**A must follow:** `b_result = UNKNOWN` **is not a rejection**; the hold must be kept (section 6).

B's result in the response only lets A know sooner. **A settles from the B records on its own subscription**, deduplicated by `(day, seq)`, so the same result arriving by two paths is never booked twice.

**Other HTTP statuses**

| Status | Meaning | What A does |
| --- | --- | --- |
| 400 | Malformed request (missing field, `qty ≤ 0`, etc.) | The order never entered D; the hold can be released |
| 409 | `ORDER_ID_CONFLICT`: the same `(user_id, order_id)` exists with different content | A bug in A; do not release the hold |
| Connection failure / A-side timeout | A does not know whether D received it | Treat the order as `UNKNOWN`; retry with the **same** `order_id`, or send a cancel |

### 2.2 Cancel `POST /v1/cancels`

**Request**

```json
{ "user_id": "u_1024", "order_id": "01JBCX3K8Q..." }
```

Cancels are not checked against the rules. D handles a cancel according to the order's state inside D (architecture document section 6):

| State inside D | What D does | Returned `action` |
| --- | --- | --- |
| Not known | Records a local tombstone; a later order with this ID is rejected | `TOMBSTONED` |
| `REJECTED_BY_D` | Nothing | `NOT_SENT_TO_B` |
| `LIVE` | Sends `CancelOrder` to B at once | `SENT` |
| `IN_FLIGHT` / `TIMED_OUT` | Sends only after `sent_at + MAX_COMMAND_AGE + CANCEL_MARGIN` | `SCHEDULED` |
| B has already given a final state | Forwards to B as usual; B answers `ORDER_ALREADY_FINAL` | `SENT` |
| Disconnected from B | Queues it and sends after reconnecting | `QUEUED` |

**Response (HTTP 202)**

```json
{
  "user_id": "u_1024", "order_id": "01JBCX3K8Q...",
  "action": "SCHEDULED",
  "send_not_before": 1793270400725
}
```

- Cancels are idempotent: repeating a cancel does not send it to B twice (D records the cancel intent).
- **A gets the cancel's result on its own B subscription**: B's `CANCELLED`, or `REJECTED` with `ORDER_NOT_FOUND` / `ORDER_ALREADY_FINAL`.
- A modify is a cancel plus a new order with a new `order_id` (as in the proposal); D has no separate modify endpoint.

### 2.3 Idempotency rules

- Idempotency key: `(user_id, order_id)`.
- A repeated order request (identical content):
  - If there is a result: return the same decision; B's result is updated to what D currently knows (for example, it was `UNKNOWN` and is now `ACCEPTED`).
  - If D is still waiting for B: wait for the same result; `NewOrder` is not sent again.
- Different content: 409 `ORDER_ID_CONFLICT`.
- Guarantee: **an approved order is sent to B at most once; an order D rejected is never sent to B.**

### 2.4 Other endpoints

| Path | Purpose |
| --- | --- |
| `GET /healthz` | 200 when ready, otherwise 503 with a body saying which condition is not met (linked accounts, B connection, caught up, storage) |
| `GET /metrics` | Prometheus format |
| `POST /admin/faults` | Fault-injection switches; exists only when `FAULTS_ENABLED=true` |

## 3. D ↔ B

Message formats, handshake and resume follow B document sections 2 and 6. What D does on its side:

| Item | What D does |
| --- | --- |
| `NewOrder` | Fields copied from A's request; `origin = USER`; `sent_at` = D's clock read just before sending |
| `CancelOrder` | Target given as `(user_id, order_id)`, `origin = USER` |
| When to send | `NewOrder` only after the decision record is committed; cancels at the times in 2.2 |
| Matching replies | Uses `(user_id, order_id)` in the `OrderEvent` to find the waiting order request |
| Connection | Connects to `ws://service-b:11659/d`; first message `{"type":"resume","from_seq":N}`. On reconnect, N = the largest seq already applied in memory; on D's restart, N = 0, rebuilding the features from the start of the day |
| Dedup and gaps | Deduplicates by `seq` and checks gaps with `prev_seq`; forwards no orders until caught up |
| End of day | After the `END_OF_DAY` cancels, clears the day's book view; once `day` changes, resume starts from 0 |
| Not sent | No orders with `origin = LIQUIDATION` in the core |

**Timeout and age limit:** we require `D_TIMEOUT ≥ MAX_COMMAND_AGE` (B document D15). D always sends a cancel for an unconfirmed order after `sent_at + MAX_COMMAND_AGE + CANCEL_MARGIN`.

**To confirm:** B's WebSocket messages need a field that tells `NewOrder` from `CancelOrder`. In B's document the order-type field is already called `type` (LIMIT / MARKET), so the two would clash. A name needs to be agreed with Bo (for example `type` for the message type, and `order_type` for the order type).

## 4. B → A: event subscription (D's requirements on B)

B defines this interface. This section only lists what D's design depends on (RD6):

- B offers a **read-only** WebSocket subscription that A connects to directly, not through D.
- The handshake is the same as D's: the first message is `{"type":"resume","from_seq":N}`; B resends outputs with `seq > N` and pushes new outputs at the same time.
- The content is the same `OrderEvent` / `Trade` that B sends to D, with identical fields.
- Read-only: this connection accepts no commands; commands can only come through D.
- If A reads too slowly, B drops A's connection without affecting matching or D's connection (the same approach as B document D16 and D21).
- A's duties: deduplicate by `(day, seq)`; check gaps with `prev_seq` and resume again when a gap is found; key the ledger on `(day, seq)`.

To confirm with Bo: port and path; how many subscribers are allowed; whether A can resume the previous day if it is down across the end of the day.

## 5. D → A: linked accounts `GET /internal/linked-groups` (provided by A)

D calls this once at start-up. Until it succeeds, D is not ready and forwards no orders.

```json
{
  "version": "seed-2026-10-01",
  "groups": [
    { "group_id": "g1", "user_ids": ["u_1024", "u_1025"] },
    { "group_id": "g2", "user_ids": ["u_3001", "u_3002", "u_3003"] }
  ]
}
```

- A user belongs to at most one group; a user in no group is a group of one.
- Links are static seed data; D does not refresh them while running.
- Alternative: A and D read the same seed file, so this endpoint is not needed. To confirm with Pin-Yun.

## 6. When A may release a hold

A releases funds only on the following facts, **never on a timeout**:

| Fact | Source | What A does |
| --- | --- | --- |
| `decision = REJECTED` | D's placement response | Release the whole hold |
| HTTP 400 | D's placement response | Release the whole hold |
| Cancel returns `TOMBSTONED` | D's cancel response | Release the whole hold (D never received this order and will reject it later) |
| `REJECTED` for the `NewOrder` (for example `EXPIRED`) | B subscription | Release the whole hold |
| `Trade` | B subscription | Settle the filled part |
| `CANCELLED` (including `END_OF_DAY`) | B subscription | Release the remaining part |
| `REJECTED` + `ORDER_NOT_FOUND` for a cancel | B subscription | Release the whole hold (D guarantees the cancel was sent after the age limit) |

What A should do after `UNKNOWN` (or a failed call to D):

1. Keep the hold and mark the order `UNKNOWN`.
2. Check its own B subscription: if an `OrderEvent` for this order has arrived, follow B's records and stop here.
3. Otherwise send `POST /v1/cancels` (a user cancel takes the same path) and wait for the result on the B subscription. If the cancel returns `TOMBSTONED`, D never received the order, so release at once.
4. If D is unavailable, the order stays `UNKNOWN` and the hold is kept; continue from step 3 when D is back. Settlement of existing orders is not affected by D.

## 7. Error codes

**D's rejection reasons (`reason` when `decision = REJECTED`); all of them mean the order was not sent to B:**

| Reason | Meaning |
| --- | --- |
| `SELF_TRADE` | Could trade against the user's own resting order |
| `WASH_TRADE` | Could trade against a linked account's resting order |
| `RISK_TIMEOUT` | No decision within `GATE_DEADLINE` |
| `RISK_UNAVAILABLE` | D is not ready |
| `CANCELLED_BEFORE_SUBMIT` | A cancel for this ID arrived earlier |

**B's rejection reasons:** as defined in B's document; currently `EXPIRED`, `ORDER_NOT_FOUND`, `ORDER_ALREADY_FINAL`, and invalid commands (unknown symbol, price or quantity off the tick/lot grid).

## 8. Sequences

### 8.1 Normal order

```
A                         D                              B
│ POST /v1/orders         │                              │
│────────────────────────►│ rules pass, write decision   │
│                         │ NewOrder(sent_at)            │
│                         │─────────────────────────────►│ journal, match
│                         │ OrderEvent ACCEPTED          │
│                         │◄─────────────────────────────│
│ 200 APPROVED / ACCEPTED │                              │
│◄────────────────────────│                              │
│ subscription: ACCEPTED, Trade …                        │
│◄═══════════════════════════════════════════════════════│
```

### 8.2 D rejects

```
A                         D
│ POST /v1/orders         │
│────────────────────────►│ R2 matches, write decision
│ 200 REJECTED WASH_TRADE │
│◄────────────────────────│
│ release hold            │        (B never receives it)
```

### 8.3 Timeout, the order never reached B

```
A                         D                              B
│ POST /v1/orders         │                              │
│────────────────────────►│ NewOrder ──────────X (lost)  │
│                         │ wait D_TIMEOUT               │
│ 200 APPROVED / UNKNOWN  │                              │
│◄────────────────────────│                              │
│ keep hold               │                              │
│ POST /v1/cancels        │                              │
│────────────────────────►│                              │
│ 202 SCHEDULED           │ wait until sent_at+AGE+MARGIN│
│◄────────────────────────│ CancelOrder ─────────────────►│
│                         │                              │ REJECTED ORDER_NOT_FOUND
│ subscription: REJECTED ORDER_NOT_FOUND                  │
│◄═══════════════════════════════════════════════════════│
│ release hold            │                              │
```

### 8.4 Timeout, the order is actually in B

```
A                         D                              B
│ POST /v1/orders         │                              │
│────────────────────────►│ NewOrder ────────────────────►│ ACCEPTED
│                         │  (D–B link drops, reply lost) │
│ 200 APPROVED / UNKNOWN  │                              │
│◄────────────────────────│                              │
│ keep hold               │                              │
│ subscription: ACCEPTED, Trade … (A's subscription is not affected by D's disconnect)
│◄═══════════════════════════════════════════════════════│
│ settle from fills, no cancel needed                    │
```

If A had already sent a cancel before seeing `ACCEPTED`, D sends it after the age limit, and B answers `CANCELLED` (the remainder is cancelled) or `ORDER_ALREADY_FINAL`. In both cases A settles from B's records, and nothing goes wrong.

### 8.5 A cancel reaches D before the order

```
A                         D
│ POST /v1/cancels        │ unknown ID, record tombstone
│────────────────────────►│
│ 202 TOMBSTONED          │
│◄────────────────────────│
│ POST /v1/orders (late)  │
│────────────────────────►│ tombstone hit
│ 200 REJECTED CANCELLED_BEFORE_SUBMIT
│◄────────────────────────│
```
