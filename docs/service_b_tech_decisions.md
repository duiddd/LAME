本文只记录**已经确定**的决策、其理由和后果。未确定的事项列在末尾「待决事项」。

## 1. 输入输出契约

### 1.1 输入:订单命令

B 只有一个上游(D),命令经同一条连接进入(D13),由日志线程按到达顺序写入当日的事件库(D19)。

| 命令 | 字段 |
| --- | --- |
| `NewOrder` | `order_id`、`symbol`、`user_id`、`side`、`type`(LIMIT / MARKET)、`price`(市价单为空)、`qty`、`origin`(USER / LIQUIDATION)、`sent_at`(D 发出该命令的 Unix 毫秒时间) |
| `CancelOrder` | 目标订单的 `(user_id, order_id)` **或** 目标订单的当日 `seq`(二选一)、`symbol`、`origin` |

`seq` 和 `ts` 不由上游提供,由 B 分配(见 D1)。上游可以用 `(user_id, order_id)` 撤单,也可以用 `OrderEvent` 返回的 `order_seq` 撤单。

### 1.2 输出

| 输出 | 内容 |
| --- | --- |
| `OrderEvent` | `day`、`seq`(本记录)、`prev_seq`、`order_seq`(该订单的 seq)、`order_id`、`symbol`、`status`(ACCEPTED / PARTIALLY_FILLED / FILLED / CANCELLED / REJECTED)、已成交量、剩余量、`reason`、`user_id`(透传) |
| `Trade` | `day`、`seq`(本记录)、`prev_seq`、`symbol`、`price`、`qty`、`taker_seq`、`maker_seq`、`user_id`(taker 与 maker 各自透传) |
| `MarketData` | 三档买卖盘快照(见 D6) |

当日所有命令与输出写在**同一个事件库**里,按 seq **全序**(跨交易对)。消费者按 `symbol` 过滤即可得到某个交易对内的有序流。

- `day`:交易日标识。`seq` 每个交易日从 1 重新开始,所以 `(day, seq)` 才全局唯一。
- `prev_seq`:事件库中**上一条输出**(`OrderEvent` 或 `Trade`)的 seq,当日第一条输出为 0。全局 seq 里还夹着命令记录,接收方看到 seq 不连续时无法判断是命令还是漏了输出;`prev_seq` 让接收方能验证自己收到的输出链是否连续。

## 2. 已定决策

### D1. seq 由日志线程在写入每条记录时分配,ts 在命令入口分配

- 事件库(D9–D11)是当日**单个 SQLite 数据库**,所有交易对共用。**日志线程**(D19)是它的唯一写入者。它在写入每条记录(命令、`OrderEvent`、`Trade`)时,从**一个计数器**取 `seq`。`seq` 即该记录在当日事件库中的顺序,当日内全局唯一、全序。
- **`seq` 每个交易日重置**,新的一天从 1 开始。`(day, seq)` 才是全局唯一的标识。
- `ts` 在命令进入日志线程时读取时钟,随命令一起写入。
- **Write-ahead 规则**:命令带着 `seq`、`ts` 提交到事件库(事务提交成功)后,才交给撮合。顺序不可颠倒。
- 重放读取事件库中已存的 `seq`、`ts`。撮合逻辑不读系统时钟,也不分配 `seq`。
- 后果:
  - 事件库归 B 所有,放在挂载卷上,容器重启后仍在。重放来源是 B 自己的事件库,不是上游队列。
  - 计数器和写入连接只有日志线程一个使用者,因此整个 B 是单实例。
  - **命令的 `seq` 是稳定的**(重放时从库中读回)。**输出的 `seq` 在写入时分配**,值取决于命令与输出在库中的交错,而这与调度时序有关,所以重放时重新算出的输出不保证得到相同的 `seq`。重放比较以内容为准(见 D10)。已写入的输出,其 `seq` 固定;续传和重发都使用库中的值。

### D2. 订单唯一标识是 B 产生的 seq,B 不做 order_id 去重

- 保证不重复是上游(D)的责任:**同一 `user_id` 在同一交易日内,`order_id` 不得重复**。
- B 假设收到的订单满足该约束,不检查 `order_id` 重复,也没有 `DUPLICATE_ORDER_ID` 这个拒绝原因。
- B 用自己分配的 `seq` 作为每个订单的唯一标识;下游事件通过 seq 引用订单。
- **seq 的范围**:每个交易日一个计数器(D1),命令与输出共用,跨交易对,每日重置。订单的唯一标识是 `(day, 其 NewOrder 记录的 seq)`。撤单所用的 seq 指当日的 seq。
- 撤单可用 `(user_id, order_id)` 或订单 seq。B 为未终结订单维护 `(user_id, order_id) → seq` 的映射;`OrderEvent` 始终带 `order_seq`,所以上游拿到后可直接用 seq 撤单。
- 上游违反约束时,B 的行为不作保证(每条命令仍获得新 seq,当作新订单处理)。

### D3. 成交不设 trade_id

- `Trade` 的标识是 `seq`,并携带 `taker_seq` 和 `maker_seq`。
- 同一对 (taker, maker) 至多成交一次(一次撮合后,要么 maker 耗尽,要么 taker 耗尽),所以 `(taker_seq, maker_seq)` 也能唯一标识一笔成交。
- `taker_seq` / `maker_seq` 引用的是当日命令记录的 seq,从事件库读回,稳定不变;成交自己的 `seq` 在首次写入事件库时固定(D1)。

### D4. user_id 作为透传字段

- B 不解释 `user_id`,只原样写入 `OrderEvent` 与 `Trade`。
- A 结算、D 构建交易者特征无需自己维护 order→user 映射。

### D5. 价格与数量使用整数 tick / lot

- 价格是 tick 的整数倍,数量是 lot 的整数倍,线上与内部均为 int64。
- 与小数的互转由 A 和前端负责。
- 目的:无浮点误差,重放逐位一致。

### D6. MarketData 只发三档快照,序号用 Unix 时间戳

- 内容:买卖各三档的价格与数量,外加最新成交价 `last_price`(最近一笔成交的价格;尚无成交时为空)。
- 每条快照是**自包含的全量**,不是增量。
- 序号为 Unix 时间戳,**在发出快照时读取当前时钟**(毫秒精度)。
- **发送频率**:同一交易对 1 ms 内最多一条;前三档或 `last_price` 相对上一条已发快照没有变化则不发。
- 时间戳必须严格递增:`ts_out = max(now, last_ts_out + 1)`,避免时钟回拨或同毫秒产生重复序号。
- 消费者规则:丢弃时间戳不大于已处理最新快照的消息,只保留最新。
- **确定性边界**:`MarketData` 是由订单簿派生的非权威视图,读时钟与限频使其内容不属于确定性重放的保证范围;确定性与可重放的是 `OrderEvent` 与 `Trade` 流(D1)。重放(恢复)期间不发布快照,追平日志后才开始发布。
- 后果:全量快照下丢失中间某条不影响正确性,因此**不再需要 gap 检测与重新同步**,提案里「clients can detect gaps and resynchronize」一句应改为「客户端只取最新快照」。更深的盘口、K 线、成交明细等不在本阶段的 MarketData 范围内,需要时另行决定。
- **心跳**:「无变化不发」会让客户端分不清「盘口没动」与「B 挂了」。因此若某交易对已满 1 秒没有发出任何快照,则重发一次当前快照(取新时间戳)作为心跳。客户端超过约定时长(如 3 秒)没有收到任何快照,即可判定 B 不可用。

### D7. 撤销不存在或已终结的订单,回 REJECTED

- 撤销一个不存在、已全部成交或已撤销的订单:输出 `OrderEvent`,`status = REJECTED`,`reason` 说明原因(如 `ORDER_NOT_FOUND` / `ORDER_ALREADY_FINAL`)。
- 订单簿不发生任何变化。

### D8. 输出流结构

- 当日所有交易对的 `OrderEvent` 与 `Trade` 同在事件库这一条全序流里,按 seq 排序。
- 消费者(A、C、D、行情服务)由此得到一致的时间线。
- **职责边界**:B 只负责把 `OrderEvent` 与 `Trade` **准确无误、低延迟**地发出去。消费者如何去重、如何使用,不在 B 的职责范围内。B 通过已记录的 seq 稳定不变(D1、D3)来为消费者提供去重的基础,但不替消费者定义去重规则。

### D9. 区分事件日志与运行日志

B 有两种性质完全不同的日志:

| 名称 | 内容 | 性质 | 存放 |
| --- | --- | --- | --- |
| 事件日志 | 当日来自 D 的 `NewOrder` / `CancelOrder`、B 内部的日终记录(D22),以及 B 产生的 `OrderEvent` / `Trade`,按 seq 排序 | 数据,状态的真相来源;按序重放,B 具有确定性 | SQLite 数据库(D11) |
| 运行日志 | 启动、重放进度、错误、慢操作 | 诊断信息,丢失不影响正确性 | stdout(`tracing` 输出到 stdout,不写文件) |

- 运行日志写 stdout:容器惯例,`docker logs` 与监控栈可直接使用,不占容器可写层,不存在 `kill -9` 时缓冲未 flush 的数据正确性问题。
- 事件日志不得放在容器可写层。容器可写层随容器重建而丢失(`compose down` 后再 `up`),不能存放它。事件日志的写入方式见 D20。
- 事件日志写入失败时,B 必须停止接单,不能降级为只打日志继续运行。
- 热路径上不输出逐单的运行日志;逐单的事实记录就是事件日志,统计走 `/metrics`。

### D10. 事件日志同时存输入与输出,恢复时校验,不一致则停机

- 事件库存放当日的命令,以及 B 产生的 `OrderEvent` / `Trade`。
- 存输出的目的是**校验**:恢复重放时,把引擎重新算出的输出与库中已存的输出逐条比对。比较内容(价格、数量、`taker_seq`、`maker_seq`、状态等),**忽略输出自身的 `seq` 与 `prev_seq`**(见 D1)。每个交易对的输出在库中保持引擎产生的顺序,按交易对分别比对。盘中崩溃重启后若发现不一致还继续撮合,会有公平性问题,因此:
  - **重放结果与已存输出不一致:B 拒绝恢复,停止服务并报错,等待人工介入。** 不得继续撮合。
- 每条记录通过 SQLite 事务原子提交,不存在写了一半的记录,无需截断尾部。
- 恢复时,库中有命令但缺少对应输出(崩溃发生在输出写入之前)的,引擎重放后补写这些输出并发送。
- 恢复只需要当日事件库:每日收盘撤掉所有未成交订单(D22),所以每个交易日都从空订单簿开始。
- 验收标准「同一订单序列重放两次产生相同成交」以成交内容为准。

### D11. 事件库是命名卷上的 SQLite 数据库

- 事件库是 Docker 命名卷上的 SQLite 数据库文件,每个交易日一个文件(如 `/data/events-<day>.db`)。数据真实存放在 Docker 宿主机侧的卷目录(`/var/lib/docker/volumes/<卷名>/_data`),容器内挂载到可配置的路径(如 `/data`);容器删除或重建后卷仍在。
- Mac 上的 Docker Desktop,卷位于 Docker 的 Linux 虚拟机内,不在 Mac 文件系统中直接可见。
- 目录由环境变量 `EVENT_DB_DIR` 配置,不写死。
- SQLite 采用 WAL 模式与 `synchronous=OFF`(与 D12 的故障模型一致)。写入由日志线程用唯一的写连接完成;补发查询用单独的只读连接,可与写入并发。
- 不使用 SQLite 的独占锁模式(它会阻止只读连接)。另用锁文件(如 `/data/b.lock`)加 `flock`,拿不到锁则退出,保证只有一个 B 实例写入。
- 往日的事件库保留,不自动删除(课程范围),仅供审计;B 不据此提供续传。
- 表结构示意(非最终):`events(seq INTEGER PRIMARY KEY, kind TEXT, symbol TEXT, ts INTEGER, prev_seq INTEGER, payload TEXT)`,`payload` 为 JSON(D17)。
- 运维约定:不使用 `docker compose down -v`,否则会删除卷。

### D12. 故障模型:只防进程崩溃,不做 fsync

- B 保证:进程崩溃、`docker kill`、容器重启后,已确认(ACCEPTED 已发出)的订单不丢。
- 写入事件库使用 `synchronous=OFF`,**不 fsync**。进程被杀后,已进入内核缓存的数据仍会被内核刷到磁盘。
- 不防整机掉电、内核崩溃、Docker 虚拟机被强杀。这超出课程项目范围,文档中不作承诺。
- 前提:ACCEPTED 必须在命令记录提交成功之后才发出(D1 的 write-ahead 顺序)。

### D13. B 与 D 之间用一条 WebSocket 连接

- `NewOrder` / `CancelOrder` 的提交,以及 `OrderEvent` / `Trade` 的输出,都只经过 B 与 D 之间的这一条 WebSocket 连接。
- B 不直接与 A、C 交互订单与成交数据:A 从 D 获得 `OrderEvent` / `Trade`(用于结算与更新订单状态);C 直接使用行情快照中的 `last_price`。这使 A 的结算依赖 D,属已接受的取舍。
- **假设**:凡是 D 发到 B 并被 B 收到的消息,都会先写入事件库(D1)。
- **B 不跟踪「哪些输出已送达」。** 续传由 D 在握手中给出起点(见 D21)。B 重发已经发过的 `OrderEvent` / `Trade` 是允许的,D 必须幂等处理(重复事件无副作用),与 D8 的职责边界一致。
- **命令超时即失败。** D 发出的命令若在约定时限内没有收到 B 的对应事件,D 视为失败,不重发命令。撮合时效性强,「一段时间内没撮合」与「撮合失败」对用户等价。

### D14. 行情发布使用独立线程,引擎任务通过无锁队列交付快照

- 引擎任务只负责把最新的三档快照交给无锁结构,**永不阻塞**、不做网络 I/O。
- 独立的行情发布线程维护所有行情订阅的 WebSocket 连接,从无锁结构取快照并发出。
- 发布线程负责 D6 中的:读取时钟打时间戳、1 ms 限频、无变化不发、1 秒心跳。因此时钟读取不在引擎任务上,与 D1 的「撮合不读时钟」一致。
- 行情服务与撮合在同一进程、同一容器内,仅以线程隔离(不再单独拆容器)。
- 订阅者各自有有界发送缓冲;慢订阅者只会丢失它自己的旧快照,不影响引擎任务与其他订阅者。
- 交付结构是有界的单生产者单消费者无锁队列。发布线程每轮取空队列,只发送最新一条。队列满时引擎任务丢弃该快照并计数(metric),绝不阻塞。假设发布线程足够快;已知风险:若发布线程停滞超过队列容量,且被丢弃的恰是一阵变化的最后一条,盘口展示会停留在旧状态,直到下一次变化。

### D15. 过期命令在入口被拒绝

- `NewOrder` 带 `sent_at`(D 发出的时间)。B 在入口分配 `ts`(D1)后,计算 `ts - sent_at`;超过配置的阈值(环境变量 `MAX_COMMAND_AGE`)则不撮合,输出 `OrderEvent`,`status = REJECTED`,`reason = EXPIRED`。
- 该命令与其 REJECTED 结果照常写入事件日志。判断只依赖已记录的 `ts` 与命令内的 `sent_at`,重放时结果一致。
- 作用:挡住 D 已超时判定失败、但命令在途中滞留(连接缓冲、B 重启后重连)而晚到的订单,避免 D3 之外的幽灵订单。
- 适用于所有 `NewOrder`,包括 `origin = LIQUIDATION`:强平由 D 持续重新评估,过期的强平单拒绝后 D 可以按当前状态重新发出。`CancelOrder` 不检查(晚到的撤单无害)。
- 约束:`MAX_COMMAND_AGE` 应不大于 D 的命令超时时限,否则 D 已判失败而 B 仍会接受。
- 依赖 D 与 B 的时钟可比较:同一台宿主机(同一内核时钟)上的容器满足;跨机器部署需另行处理时钟偏差。
- **不覆盖的情形**:B 已及时接受了订单,但 `ACCEPTED` 回复延迟或丢失,D 超时判失败。此时订单实际在订单簿里。需要 D 超时后补发 `CancelOrder`(B 对已终结订单回 REJECTED,无害),这是 D 的职责。

### D16. 发送背压不是 B 的职责

- D 处理过慢由 D 自己解决(D 有命令超时,B 有 D15 的过期拒绝)。B 不对 D 限流,也不因 D 慢而停止撮合。
- B 的唯一义务:**引擎任务不得因 D 读取慢而被阻塞**。B 暴露「待发送输出的积压量」作为 metric。

### D17. 所有序列化使用 JSON

- WebSocket 线上格式与事件日志的记录格式均为 JSON。

### D18. 不使用忙等;撮合引擎是 tokio 里的纯计算任务

- 不使用忙等:占满 CPU、与其他服务争用,且收益被 JSON 与 WebSocket 的开销淹没。
- 每个交易对一个撮合引擎任务,运行在 tokio 上。引擎**只做内存计算,不做任何 I/O(包括文件写入)**,因此不会阻塞 tokio 的工作线程。
- 单次处理保持短;连续处理一批命令时中途让出(`yield`)。
- 任务之间使用 tokio channel 通信。

### D19. 任务模型:单进程,日志线程是事件库的唯一写入者

```
D ──WebSocket── [连接任务:读半 / 写半]
                    │ 收到命令
                    ▼
        [日志线程]  ① 打 ts、分配 seq、把命令事务提交到事件库
                    │ ② 交给对应交易对的引擎任务
                    ▼
       [引擎任务 × 每个交易对,纯计算]
                    │ 撮合,产生 OrderEvent / Trade
                    ▼
        [日志线程]  ③ 分配 seq 与 prev_seq、把输出事务提交到事件库
                    │ ④ 交给连接任务的写半
                    ▼
                [连接任务·写半] ── WebSocket ── D
```

- **日志线程是专用的操作系统线程**(不是 tokio 任务):SQLite 的写入是同步阻塞调用,放在 tokio 工作线程上会阻塞其他任务。它与 tokio 任务之间用 channel 通信。
- 日志线程**常驻**,持有写连接和 seq 计数器,生命周期不依赖 WebSocket 连接。D 断线时,引擎里已有的命令产生的输出仍会被写入事件库。
- 顺序保证:命令先提交再撮合(D1);输出先提交再发送。D 看到的输出一定已在事件库里。
- 日志线程可以一次取出 channel 中当前所有待写记录,放在一个事务里提交,提交后再逐条交付(实现优化,不改变上述顺序保证)。
- 连接任务的**读半与写半分开**,各自独立:D 读得慢导致发送卡住时,不影响接收 D 发来的命令。
- 行情快照由引擎任务交给无锁队列,行情发布线程取走发送(D14),不经过日志线程。
- 事件库只有一个写入者,B 是**单进程**:一个进程内有连接任务、日志线程、每个交易对一个引擎任务,以及行情发布与 HTTP。

### D20. 事件日志由专用写入器写入,运行日志由 tracing 写 stdout

- 日志线程直接使用 SQLite(`rusqlite`)写入事件库。**不使用 `tracing`**。
- 原因:日志线程必须知道每一次写入是否成功;写入失败时 B 停止接单(D9)。`tracing` 的调用没有返回值,写入失败无法传回调用方;且存在异步丢行、按时间滚动文件、被日志级别过滤关掉等不适合承载数据的行为。
- 运行日志(系统状态)使用 `tracing` 输出到 stdout(D9);它是诊断信息,丢失不影响正确性。

### D21. D 重连后的续传协议

- D 每次连上 B,**第一条消息**必须是握手:`{"type":"resume","from_seq":N}`,含义是「请发**当日** seq 大于 N 的所有输出」;`0` 表示从当日开头开始。只支持恢复当日,不支持跨日恢复:D 崩溃后只应请求当日的数据。B 只发 `OrderEvent` 与 `Trade`,不发命令记录。
- B 同一时刻只保留**一条** D 的连接;新连接到来时关闭旧连接(可能是 D 崩溃后留下的半开连接)。
- 握手后,B **照常实时发送**新的输出,同时由补发任务用只读连接查询当日事件库中 `seq > from_seq` 的输出(`WHERE seq > ? AND kind IN ('OrderEvent','Trade') ORDER BY seq`),发给 D。
- **B 不保证补发与实时之间的先后,两者可能交错、重复。** 各自内部按 seq 升序。「接上而不漏」由 D 负责:D 按 `seq`(当日内)幂等去重,用 `prev_seq` 验证输出链是否连续(D16 的职责划分)。
- 补发与实时共用同一个出站队列。队列有上限(环境变量 `OUTBOUND_QUEUE_CAP`,默认 10000 条左右);队列满则**关闭该 WebSocket 连接**,B 继续撮合已有命令并照常写入事件库,D 重连后用握手续传。补发任务因此也受队列反压。
- B 定期发送 WebSocket ping(超时约 10 秒未收到 pong 则关闭连接),只用于更快发现半开连接,不影响正确性:续传依据始终是 D 在握手中给出的起点。
- 握手被拒绝的情形(B 返回错误并关闭):`from_seq` 大于当日事件库的最大 seq(说明 D 的状态领先于 B,B 丢过数据,需人工处理)。

### D22. 交易日结束时 B 被动撤销所有未成交订单,seq 重置

- 日终撤单不是主动撤单,也**不是 D 发来的命令**。交易日结束时,B 自己撤销全部未成交(resting)订单,对每个订单输出 `OrderEvent`,`status = CANCELLED`,`reason = END_OF_DAY`,和其他输出一样发给 D。
- **为保证确定性,日终必须在事件库中留下一条 B 内部的记录。** 日志线程在判定交易日结束时,先写入一条 `DayClose` 记录(它是 B 自己产生的内部记录,不是外部命令),再由引擎按订单 seq 的顺序撤单。这样重放时引擎遇到 `DayClose` 会做同样的撤单,与已存的 `END_OF_DAY` 输出一致;如果崩溃发生在撤单中途,恢复也能续上。没有这条记录,重放不会产生这些撤单,会与已存输出不一致,违反 D10。
- 撤单完成后,B 关闭当日事件库,开启新交易日的事件库:`day` 更新,seq 从 1 重新开始,订单簿为空。
- 由此恢复只需要当日事件库(D10)。

### D23. 容器布局

**镜像**
- 多阶段 Dockerfile:构建阶段用固定版本的 Rust 镜像,配合 `rust-toolchain.toml` 并提交 `Cargo.lock`,保证可重复构建。
- SQLite 使用 `rusqlite` 的 `bundled` 特性,编译进二进制。
- 运行阶段使用 `gcr.io/distroless/cc-debian12`,以非 root 用户运行。
- 镜像里只有撮合引擎;bots 与压测是另外的镜像。

**端口**

| 端口 | 内容 | 暴露范围 |
| --- | --- | --- |
| 9999 | WebSocket `/md/<symbol>`(行情) | 映射到宿主机,供前端直连 |
| 11659 | WebSocket `/d`(D 通道)、HTTP `/healthz`、`/metrics` | 映射到宿主机;以 **IP 白名单**限制来源(见下) |

- 11659 的白名单由 B 在应用层按连接的对端 IP 检查,允许的 CIDR 列表由 `CTRL_ALLOWED_CIDRS` 配置,不在名单内的连接直接拒绝。白名单只限制来源,不是身份认证(真实认证不在项目范围内)。
- 9999 不做限制。

**目录与权限**
- 命名卷挂载到 `/data`,内含 `events-<day>.db`(及 SQLite 的 `-wal`、`-shm`)和 `b.lock`。
- 镜像内预先创建 `/data` 并归运行用户所有,使命名卷首次挂载时沿用该属主。
- 根文件系统只读(`read_only: true`),唯一可写位置是 `/data`。SQLite 设 `PRAGMA temp_store=MEMORY`,避免在别处写临时文件。

**配置**

| 配置 | 含义 |
| --- | --- |
| 配置文件(挂载进容器) | 交易对及其 tick / lot |
| `MD_ADDR` | 行情监听地址,默认 `0.0.0.0:9999` |
| `CTRL_ADDR` | D 通道与健康检查监听地址,默认 `0.0.0.0:11659` |
| `CTRL_ALLOWED_CIDRS` | 允许连接 11659 的来源网段列表 |
| `EVENT_DB_DIR` | 事件库目录,默认 `/data` |
| `MAX_COMMAND_AGE` | D15 的过期阈值 |
| `OUTBOUND_QUEUE_CAP` | D21 的出站队列上限 |
| `RUST_LOG` | 运行日志级别 |

**信号与退出**
- 显式处理 `SIGTERM`(`tokio::signal`):停止接新命令,让引擎与日志线程处理完手头的记录后退出。compose 设 `stop_grace_period: 10s`。
- 这只为整洁,不是正确性的依赖:D12 的保证对 `SIGKILL` 同样成立。

**健康检查与启动顺序**
- 二进制自带 `--healthcheck` 子命令,compose 以 exec 形式调用(镜像内无 `curl`)。
- `/healthz` 在重放完成之前返回不健康(恢复期间不接单、不发行情,D10);compose 设足够的 `start_period`。
- D 通过 `depends_on: condition: service_healthy` 等待 B 就绪。compose 文件整体归 A 维护,B 提供自己服务的片段。

**重启与资源**
- `restart: unless-stopped`:崩溃后自动拉起并重放。
- 不设 CPU 限制;内存设宽松上限。
- stdout 日志使用 `json-file` 驱动并限制大小(`max-size: 10m`、`max-file: 3`),因为 Docker 默认不限制容器日志大小。

**时区与时钟**
- 容器内统一 UTC;同一宿主机上的容器共用内核时钟,满足 D15 对时钟可比的要求。

**待实测验证**:(1)通过映射端口进入容器的连接,其对端 IP 可能已被 Docker 的网络转换改写(例如 Docker Desktop 上宿主机发起的连接常显示为虚拟机网关地址),基于对端 IP 的白名单是否按预期生效,取决于 D 的部署位置:同一 compose 网络内的容器之间看到的是容器 IP,需要把 compose 网络的网段(最好固定子网)写进白名单。(2)`read_only` 根文件系统加非 root 用户加命名卷的权限组合,只有真正运行时才能确认。实现阶段首先要跑通的是「容器启动 → `docker kill` → 自动重启 → 恢复一致」。
