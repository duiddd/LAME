ADR-001

Synchronous Pre-Trade Risk Gate (Service D) Failing Closed

COMP41720 LAME · Decision Owner: Zongyan Yang (Service D) · Team Aligned (A, B, C, D)
ACCEPTED · VERDICT: ACCEPT
Updated with 20 Nov 2026 live compose run
Decision Summary: Position Service D (:8400) as a single-instance, synchronous, rule-based pre-trade gate directly between A and B. Every order, cancel, and modify passes through D, failing closed on overload or outage so zero unvetted self-trades or wash trades ever execute on B.
1. Context & Load-Bearing Constraints

LAME must prevent self-trading (R1) and wash trading across seeded linked accounts (R2). Once an order enters Service B's matching thread and executes, fills are final; reversing ownership violates price-time priority for the counterparty. B replays its daily SQLite journal (events-<day>.db) bitwise after a crash and accepts only one upstream command WebSocket (/d). Therefore any risk check must precede B, operate deterministically, and respect that single command channel. Under overload or failure, the gate must choose between allowing unchecked orders (fail open) or refusing them (fail closed).

Revisit / Flip Conditions: Reconsider if, under target bot load, load shedding refuses more legitimate orders than tolerable, or if B adds multiple command channels and a post-execution trade reversal mechanism.

2. Decision (Active Voice)

Zongyan Yang decided that D (:8400) operates as a single-instance, synchronous, deterministic gate between A and B carrying all trading commands (new, cancel, modify):

  • Deterministic Pure Rules (R1, R2): Rules read zero clocks, zero randomness, and zero external I/O, evaluating strictly against the order, D's in-memory full book view, and linked_accounts.json. Each decision records (decision_no, features_seq, rule_version) in SQLite WAL before forwarding to B.
  • Synchronous 202 / Fail-Closed 503 + Ordered Outbox: D stores valid orders (202 receipt) or refuses immediately (503 RISK_UNAVAILABLE / RISK_BUSY with nothing stored) and pushes outcomes via its ordered notification outbox (notify_seq).
  • Queue Cap, Deadline & Load Shedding: D enforces DECISION_QUEUE_CAP = 1,000 and a 500 ms gate deadline (RISK_TIMEOUT), while A sheds new orders before D's queue grows rather than disabling R2 under load.

4. Alternatives Considered & Rejected
  • Post-trade asynchronous surveillance: Keeps trading fast and off-path, but self-trades and wash trades execute and settle irreversibly in B before detection.
  • ML / LLM classifier inside D: Catches subtler manipulation, but hundreds of milliseconds of latency and non-deterministic drift break bitwise crash replay.
  • Degrade by dropping R2 (keep R1 only) under load: Preserves higher availability during bursts, but opens the cross-account wash-trading window precisely when an attacker floods the gate.
ADR-002

Spot Funds Remain Held Until Service D's Notification Settles Order Fate

COMP41720 LAME · Decision Owner: Pin-Yun Kuo (Service A) · Team Aligned (A, B, C, D)
ACCEPTED · VERDICT: ACCEPT
Updated with 20 Nov 2026 fault & consistency runs
Decision Summary: Once an order request may have reached Service D, Service A settles or releases held funds only upon receiving D's ordered notification (notify_seq) — never on an HTTP timeout or 202 acknowledgement — guaranteeing zero spot overdrafts (CHECK (available >= 0)).
1. Context & Load-Bearing Constraints

Service A (:8000, PostgreSQL) is the sole writer of balances, holds, and order state. Spot trading enforces a hard zero-overdraft invariant: CHECK (available >= 0). Any settlement violating it halts settlement across all users by design. When placing an order, A locks the hold in Postgres and sends HTTP POST /v1/orders to D, whose 202 response confirms queued receipt only. Actual outcomes (rejected, accepted, fills, cancels) arrive asynchronously via contiguous notify_seq pushes from D's outbox (applied sequentially at 29–46 notify/s on a test laptop). An HTTP timeout is therefore ambiguous: D or B may already hold the live order.

Revisit / Flip Conditions: Revisit if D returns final matching outcomes synchronously in the HTTP call, if B guarantees rejecting commands older than A's 2 s timeout (turning timeout into "never placed"), or if users prefer occasional manual overdraft repair over brief fund freezes.

2. Decision (Active Voice)

Pin-Yun Kuo decided that once an order request may have left A, funds move strictly on D's notifications:

  • Immediate Release Only on Known Non-Send: Connection refused before send, or D returning synchronous 503 (saving no record), rejects and releases the hold at once.
  • UNKNOWN Hold Protocol: An unanswered send becomes UNKNOWN (shown as "Confirming" in React UI, which warns users not to re-submit); the hold stays while A retries the identical order_id (D deduplicates) for up to the 5 s resend window before switching to cancellation, then cancels (tombstoned at D if unseen, rejecting any later order with CANCELLED_BEFORE_SUBMIT; B stores no tombstones and returns OrderNotFound), releasing funds only after D's notification confirms cancellation/rejection.
  • Ordered Idempotent Settlement: A locks its notify_seq cursor row FOR UPDATE, returns 409 {"expected_seq": N} on sequence gaps so D rewinds cleanly, and deduplicates fills by B's (day, seq).

4. Alternatives Considered & Rejected
  • Release hold on HTTP timeout: Restores user cash after 2 s, but an in-flight order already in B can fill against re-spent cash and breach CHECK (available >= 0), freezing global settlement.
  • Two-Phase Commit (2PC) across A, D, B: Avoids UNKNOWN state, but stalls B's single sequential matching thread behind PostgreSQL locks and breaks crash recovery cleanly.
ADR-003

Decouple AI Market Analyst (Service C) Off the Critical Trading Path

COMP41720 LAME · Decision Owner: Rushabh Mutha (Service C) · Team Aligned (A, B, C, D)
ACCEPTED · VERDICT: ACCEPT
Updated with 20 Nov live + fault-injection runs
Decision Summary: Isolate Service C (:8080) as an independent off-path architecture quantum using asynchronous RabbitMQ ingestion (with DLQ), local SQLite FTS5 BM25 retrieval, passive read-only Service B WebSocket snapshots, and bounded 3.0 s Ollama RAG — ensuring zero latency or failure propagation to A → D → B.
1. Context & Load-Bearing Constraints

LAME couples a deterministic spot exchange (A → D → B) with an AI analyst (C) running RAG over local Ollama (llama3.2:1b). Three constraints clash at this boundary: (1) Latency & Determinism: order placement requires sub-second millisecond-bounded tail latency and bitwise replay, whereas LLM calls span 0.4 s to a 3.0 s timeout; (2) Consistency Divide: A's spot holds demand strict CP guarantees, whereas market explanations tolerate AP eventual consistency if freshness timestamps are disclosed; (3) Trust Boundary: external news feeds and chat prompts carry untrusted text (prompt injection, malformed JSON) that cannot share a failure domain or schema with A's ledger or B's journal.

Revisit / Flip Conditions: Revisit only if product scope mandates AI-scored risk gating inside D's synchronous path or blocks spot trading whenever news ingestion lags.

2. Decision (Active Voice)

Rushabh Mutha decided to keep Service C off the trading path as a separate architecture quantum with zero synchronous inbound calls from A, D, or B:

  • Private Search Store: C owns an isolated SQLite WAL database (news_c.db) using deterministic FTS5 BM25 with atomic index_version, sharing zero databases with peers.
  • Async RabbitMQ + DLQ Ingestion: Scripted and activity news events traverse news.direct → news_tasks with idempotent news_id deduplication; malformed payloads nack(requeue=False) via news.dlx into news.dlq.
  • Passive Read-Only Snapshots: C subscribes to B's /md/<symbol> WebSocket into an in-memory MarketDataCache, dropping ts_ms < existing, refreshing liveness when B re-sends an unchanged MarketData snapshot (same last_ms, no separate heartbeat flag), resetting watermarks on reconnect, and flagging is_stale = true after 3.0 s of silence.
  • Guardrails, Spend Gate & Bounded Calls: C screens injections/advice pre-LLM (REJECTED_UNSAFE), short-circuits empty BM25 hits pre-LLM (INSUFFICIENT_EVIDENCE), enforces temperature = 0.0 JSON Schema output + post-LLM citation verification, and caps Ollama at 3.0 s with UI fallback.

4. Alternatives Considered & Rejected
  • Embed RAG inside Service A: Removes one container and CORS surface, but exposes balance-hold worker threads and PostgreSQL pools to 3 s LLM brownouts and untrusted prompts.
  • Synchronous REST from C to A/B per question: Avoids MarketDataCache, but couples chat traffic bursts directly onto trading engines.
  • Vector embeddings DB + Saga coordination: Vector runtime adds VRAM/latency drift; Sagas are unneeded for read-only explanations with zero state mutations.
