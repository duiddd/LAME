## 2. 已定决策

### D1. 语言与框架:Python 3.12 + FastAPI

- **决策:** A 使用 Python 3.12、FastAPI、Pydantic v2。
- **理由:**
  1. 与 C 使用同一套技术,compose、Dockerfile、监控接入方式可以共享。
  2. FastAPI 原生 async,适合 A「大部分时间在等数据库和下游」的 I/O 密集型负载。
  3. Pydantic 在 API 边界完成类型与格式校验,错误信息自动带字段名。
- **备选:** Java + Spring Boot(负责人更熟悉,事务生态成熟,但内存占用大,与组内其他服务不一致);Go。
- **后果:**
  - Python 的单进程吞吐低于 JVM 或 Go。A 的瓶颈在数据库事务和下游等待,不在 CPU,预计可接受;Week 6 基线测量后确认。

### D2. 单进程、单 worker

- **决策:** uvicorn 只开 **1 个 worker**。限流的令牌桶、熔断器状态、负载削减的延迟窗口、事件消费任务都放在进程内存中。
- **理由:** 多 worker 等于多个进程,每个进程各有一份内存状态:限流会按 worker 数放大,事件会被重复消费。单进程最简单,也与 B 的单实例设计一致。
- **备选:** 多 worker + Redis 集中保存限流和熔断状态。
- **后果:**
  - 只用到一个 CPU 核心。
  - **改变决策的事实:** 若 Week 6 基线显示 A 单进程无法达到目标下单速率,就改为多 worker + Redis,事件消费拆为独立进程。

### D3. 端口与适配器(Ports & Adapters)

- **决策:** A 的核心逻辑只依赖四个端口(见 1.3),每个端口在通信方案确定后实现一个适配器。测试时用内存假实现替换。
- **理由:** 服务间通信方式尚未确定。把「A 需要什么语义」和「用什么协议传」分开,通信方案改变时只换适配器,订单状态机和账本逻辑不受影响。
- **后果:**
  - 多一层接口。
  - 端口语义(尤其「未知」这一结果、连续编号)是 A 对通信方案的硬性要求,讨论通信方式时以此为输入。

### D4. 三层幂等

| 层 | 防止的重复 | 键 | 实现 |
| --- | --- | --- | --- |
| 请求层 | 用户连点、HTTP 重发 | 前端生成的 `client_request_id` | `UNIQUE (user_id, client_request_id)`,重复请求返回已有订单 |
| 订单层 | 重试导致同一订单两次进入撮合 | A 生成的 `order_id`(ULID),经 D 原样带到 B | 每单只生成一次;下游去重待对齐 |
| 结算层 | 同一笔成交或事件被处理两次 | 成交自身的唯一标识与流编号,**不用 `order_id`** | `applied_trades`、`ledger_entries` 唯一约束、`stream_cursors`,与结算同一事务 |

- **理由:**
  - 只靠 A 生成的 key 挡不住连点:两次点击是两个请求,A 会生成两个不同的 `order_id`。所以需要前端先生成请求键。
  - 一张订单可以分多次成交,这些成交的 `order_id` 相同。用 `order_id` 去重结算会把第二笔成交误判为重复,账会少算。
- **`order_id` 用 ULID:** 全局唯一且按时间有序,满足 B 的「同一 user 同一交易日内 `order_id` 不重复」契约(B D2),排序和排查也方便。

### D5. 超时不释放冻结资金;订单需两个条件同时满足才结案

- **决策:**
  1. 调用 `RiskGatewayPort` 超时,订单进入 `UNKNOWN`,**冻结资金保留**。`fate` 模块以指数退避(1 s、2 s、4 s,上限 30 s)反复发送撤单,直到收到终结事件。
  2. 冻结资金只依据订单事件和成交释放(规则见架构文档 5.2)。终结事件只释放**未成交部分**,已成交部分等对应成交结算后才处理。
  3. 订单「结案」需要两个条件:状态为终结状态,**且**已结算数量等于累计成交量。
- **理由:**
  - 超时只代表「没收到回应」,不代表「对方没做」。订单可能已在 B 的订单簿上,此时释放资金,之后成交就会用到已释放的钱。
  - 订单事件和成交可能来自不同的流,先后不保证。若收到 CANCELLED 就全部释放,晚到的成交会没有资金可结算。
- **后果:**
  - 下游不可用期间,`UNKNOWN` 订单的资金一直冻结。这是提案已接受的代价:冻结资金换取永不以已释放资金成交。
  - 依赖下游对「撤销一个未见过的订单」给出明确答复,并拒绝该订单晚到的原单(见待对齐事项)。

### D6. 数据库:PostgreSQL + SQLAlchemy 2 Core(async)+ asyncpg + Alembic

- **决策:** 账本与订单存于独立的 PostgreSQL 容器。使用 SQLAlchemy Core 手写 SQL(不用 ORM),Alembic 管理表结构版本。
- **冻结用一条条件更新完成:**
  `UPDATE accounts SET available = available - :amt, held = held + :amt WHERE user_id = :u AND asset = :a AND available >= :amt`
  影响 0 行即余额不足。插入订单、冻结、写流水在同一事务内提交。
- **理由:**
  1. 余额需要强一致与行级锁;多用户并发写入时,SQLite 单写者会成为瓶颈。
  2. 条件更新本身就是原子操作:不需要先读后写,不会出现两张单同时读到「余额够」的竞态,也不会死锁、不需要重试。
  3. 表上加 `CHECK (available >= 0 AND held >= 0)`,即使代码有错,数据库也拒绝出现负余额。
  4. Core 的 SQL 显式可见,没有 ORM 的隐式加载与自动 flush。
- **备选:** `SELECT ... FOR UPDATE` 悲观锁(正确,但多一次往返);乐观锁版本号(争抢同一账户时反复重试);SQLite(与 B、C 一致,但单写者)。
- **后果:** compose 多一个 PostgreSQL 容器和命名卷。

### D7. 结算与游标同一事务,实现等效一次

- **决策:** 每处理一条输入(成交或订单事件),在**同一事务**内完成:余额变动、写流水、记录已处理标识、推进该流的游标 `stream_cursors(stream, day, last_no)`。
- **理由:** 投递是至少一次,上游还可能重放。结算和游标一起提交,A 崩溃重启后从游标继续,重复输入被唯一约束挡下,效果上就是恰好一次。
- **缺号处理:** 收到的编号不连续时,暂停应用该流,请求补发缺失区间,补齐后继续。
- **兜底对账:** 若某订单的累计成交量大于已结算数量超过设定时长,判定有成交缺失,请求补发。这一层不依赖上游提供连续编号。
- **后果:** 每条输入一次数据库事务;Week 6 基线测量后确认吞吐足够。

### D8. 金额一律用整数

- **决策:** 价格以 tick 的整数倍、数量以 lot 的整数倍表示;余额以各资产的最小单位存为 `BIGINT`。只在 API 边界用 `Decimal` 与十进制字符串互转。**全系统不使用 float。**
- **理由:** 与 B 的整数 tick/lot 一致(B D5),无浮点误差,账本加总逐位可验证。
- **后果:** tick、lot、各资产最小单位放在与 B 共用的交易对配置文件中,只维护一份。

### D9. 限流:每用户内存令牌桶

- **决策:** 每个用户一个令牌桶,初始值为每秒 5 单、突发 10 单。撤单使用独立且容量更大的桶,保证用户随时能撤单。参数可配置。
- **理由:**
  1. 令牌桶允许短暂突发,同时限制平均速率,符合人工交易的使用模式。
  2. A 是单进程(D2),不需要 Redis。
  3. 撤单是降低风险的操作,不应被下单配额挡住。
- **备选:** 固定时间窗计数(窗口边界会允许两倍突发);Redis 集中式限流(多实例才需要)。
- **后果:**
  - A 重启后桶会重置,短时间内限流偏松,可接受。
  - 限流保护的是「单个用户太快」;保护「整个系统过载」的是负载削减(D13),两者分开。

### D10. 订单大小管理:按交易对的静态配置

- **决策:** 每个交易对配置 `tick`、`lot`、`min_qty`、`max_qty`、`max_notional`。价格须为 tick 的整数倍,数量须为 lot 的整数倍,名目金额 = 价格 × 数量,不得超过 `max_notional`。市价单以保护价(D11)估算名目金额。
- **理由:** 与 B 共用同一份配置,避免两边规则不一致导致「A 放行、B 拒绝」。
- **备选:** 按用户分级限额(超出本项目需要)。
- **后果:** 修改限额需要重启 A,可接受。

### D11. 价格保护

- **决策:**
  - 限价单价格须在参考价 ±10% 以内。
  - 市价单需要不超过 3 秒的参考价,否则以 `NO_FRESH_PRICE` 拒绝(fail-closed)。
  - 市价买单按「卖一价 × 1.05」、市价卖单按「买一价 × 0.95」计算保护价,用于名目金额检查与冻结金额。
- **理由:** 防止明显输错的价格;市价单的成交价在下单时未知,需要一个上限才能确定冻结金额。
- **后果:** 若撮合端的市价单没有价格上限,薄盘口下实际成交金额可能超过冻结金额(见待对齐事项)。

### D12. 下游调用:超时、重试、熔断

- **决策:**
  - 调用分别设置连接超时和总超时;总超时取 A 在延迟预算中的份额。
  - **新单只在请求确定没有发出(连接被拒)时重试**,使用同一个 `order_id`;超时后不重试,直接进入 `UNKNOWN`(D5)。
  - 撤单可无限重试(重复撤单无害)。
  - 熔断器自行实现(约 40 行):连续 5 次失败或超时则打开,10 秒后半开,放行 1 个试探请求。打开期间,新单在**冻结资金之前**就以 `SYSTEM_BUSY` 拒绝;撤单不经过熔断器,改为排队重试。
- **理由:** 区分可重试与不可重试:连接被拒说明请求没有离开 A,重试安全;超时则可能已被处理,重试有重复下单风险。熔断在冻结前判断,避免为注定失败的订单冻结资金。自行实现熔断器逻辑透明,不引入以同步为主的第三方库。
- **备选:** pybreaker、tenacity 等第三方库。
- **后果:** 熔断参数需在故障注入测试中调整。

### D13. 负载削减在 A,D 的规则始终开启

- **决策:** A 维护 30 秒滑动窗口内的风控调用延迟。连续三次(每秒评估一次)p99 超过风控在预算中的份额,就以 `SYSTEM_BUSY` 拒收新单;p99 回落到阈值的 80% 以下才恢复。撤单永不削减。
- **理由:** 实现提案中降级模式的决策:过载时在入口拒单,而不是关闭 D 的跨订单规则。在 A 本地测量,不依赖监控系统。回滞(80%)避免在阈值附近反复切换。
- **后果:**
  - 过载时部分用户无法下单(用可用性换保护)。
  - 阈值由 Week 6 基线确定。

### D14. 推送前端使用 SSE

- **决策:** `/api/stream` 以 Server-Sent Events 推送该用户的订单与余额更新;重连时先推一次当前快照。
- **理由:** A 只需单向推送;SSE 比 WebSocket 简单,浏览器原生自动重连。
- **备选:** WebSocket(双向,但 A 用不到)。
- **后果:** 若之后需要客户端经同一连接发送消息,改为 WebSocket。

### D15. 前端:React + Vite + TypeScript,A 负责外壳

- **决策:** 前端是全组共用的一个应用。A 负责应用外壳、下单、挂单列表、余额与成交;C 提供新闻与问答组件。构建为静态文件,由 nginx 容器提供。行情由前端直接从行情源获取,不经过 A。
